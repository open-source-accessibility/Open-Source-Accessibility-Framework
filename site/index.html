Open Source Accessibility

Accessibility, built into how your project already works

Open source software powers most of the world's technology, and much of it still cannot be used by people with disabilities. This framework breaks that problem into five phases a maintainer can actually work through, starting with the files already in the repository and ending with a project that keeps its accessibility gains after the people who made them move on.

  • Join the open source accessibility organization

Five phases

The phases are ordered, not optional. Each one assumes the work in the phase before it, so a project that skips ahead to testing usually ends up with a backlog it has no process for clearing. Work through them in order, at whatever pace your maintainers can sustain.

  1. Phase 01 Foundational

    State the commitment, name an owner, and fix the accessibility of the project's own front door.

  2. Phase 02 Workflow

    Put accessibility into issues, pull requests, and CI so it is checked before code lands.

  3. Phase 03 Testing

    Layer automated checks, manual passes, and assistive technology testing into a repeatable routine.

  4. Phase 04 Community

    Make contributing possible for disabled developers and make their reports count.

  5. Phase 05 Sustaining

    Measure the work, fund it, and hand it off so progress survives maintainer turnover.

Phase 01 Foundational

State the commitment in writing, give it an owner, and make the project's own documentation and interface usable.

Most projects have no accessibility problem statement, no owner, and no way for a user to report a barrier. Everything later in the framework depends on closing that gap first, and almost all of it is documentation work rather than code.

Start here

  • Publish an accessibility statement. Add an ACCESSIBILITY.md that says what the project commits to, which standard it targets, what is known to be broken, and how to report a barrier.
  • Pick a conformance target. WCAG 2.2 Level AA is the working default for most web interfaces. Command line tools, editors, and native apps need an equivalent stated baseline rather than no baseline.
  • Name someone accountable. One maintainer owns accessibility triage. Unowned accessibility work is the first thing dropped when a release gets tight.
  • Add an accessibility issue template. Ask for the barrier, the assistive technology and version, the platform, and the expected behavior. Add a label so the issues can be found later.
  • Fix the front door. The README, the docs site, and the project website are what a disabled developer meets first. Check heading order, alt text, link text, contrast, and reading order there before touching product code.
  • Write down the known barriers. An honest list of what does not work yet is more useful to users than a claim of full conformance, and it becomes the backlog for the next phase.
  • Say disability out loud in the code of conduct. Inclusion that is only implied is not something a contributor can point to when they need it.

Signals of progress

  • An ACCESSIBILITY.md exists at the repository root and names a target and a contact.
  • Accessibility issues have a dedicated label and at least one template.
  • A user can report a barrier without knowing anyone on the team.
  • The project's own documentation passes a keyboard and heading structure check.

Phase 02 Workflow

Move accessibility from a review someone remembers to do into the contribution process itself.

Open source workflows tend to push accessibility to the end of a cycle, where fixing an issue costs far more than building it in would have. The work in this phase is making the default path through your repository produce accessible code, so contributors do not have to be accessibility experts to avoid regressions.

Start here

  • Put accessibility in the definition of done. Document it in CONTRIBUTING.md so the expectation is visible before someone opens a pull request, not after.
  • Add a pull request checklist. Keyboard operable, visible focus, accessible name, contrast checked, no meaning carried by color alone, tested at 400 percent zoom. Keep it short enough that people read it.
  • Automate the checks a machine can make. Run a linter such as eslint-plugin-jsx-a11y in pre-commit and an engine such as axe-core, pa11y, or Lighthouse CI on pull requests.
  • Fail on new violations, not on the whole backlog. Baseline the existing issues so CI blocks regressions without blocking every contributor on day one.
  • Write acceptance criteria into feature issues. Describe the keyboard interaction and the expected screen reader announcement while the feature is being specified.
  • Adopt an upstream first rule. When a barrier comes from a dependency or shared component, fix it there and track the local workaround until the upstream fix ships.
  • Triage by user impact. Rank a blocked task for a screen reader user above a cosmetic contrast miss, and write the severity scale down so triage is consistent between maintainers.

Signals of progress

  • Automated accessibility checks run on every pull request and their rule coverage is documented.
  • Accessibility appears in CONTRIBUTING.md and in the pull request template.
  • New accessibility regressions are caught before merge rather than reported by users.
  • Barriers found in dependencies are filed upstream and linked from the local issue.

Phase 03 Testing

Combine automation, manual review, and assistive technology testing into a routine anyone can repeat.

Automated tools catch a useful but small share of accessibility defects, and they cannot judge whether an experience makes sense. Comprehensive testing needs manual effort and specialist knowledge that most teams do not have on hand, so the goal of this phase is a documented procedure that a non-specialist maintainer can follow and get the same answer twice.

Start here

  • Run the keyboard pass first. Tab through every flow. Check reachability, focus visibility, logical order, no traps, and that every mouse action has a keyboard equivalent. It is the cheapest test with the highest yield.
  • Test with real assistive technology. Cover at least one screen reader per platform you support, such as NVDA or JAWS with Windows browsers, VoiceOver on macOS and iOS, TalkBack on Android, and Orca on Linux.
  • Check reflow and text spacing. View at 400 percent zoom in a 1280 pixel viewport, and apply increased line and letter spacing. Content should not be cut off, overlapped, or require two dimensional scrolling.
  • Verify state, not just structure. Errors, loading, expanded and collapsed, selected, and live region updates are where most real barriers live.
  • Publish the test procedure. Write the steps, the tools, and the versions into the repository so results are reproducible and a new contributor can run them.
  • Add a regression test with every fix. Unit and integration assertions on accessible name, role, and focus behavior keep resolved bugs from returning.
  • Report what you found. A short conformance summary or accessibility conformance report tells downstream projects what they are inheriting.

Signals of progress

  • The assistive technology and browser combinations under test are named in the repository.
  • Manual test steps are written down and have been run by more than one person.
  • Fixed accessibility bugs have regression tests attached.
  • Test results are published where users and downstream maintainers can read them.

Phase 04 Community

Close the distance between the people who build the software and the people who depend on it being accessible.

Developers usually work in isolation from the users who rely on accessibility features, and that distance is where barriers get designed in. Without disabled people involved in the work, teams miss the insight that would have prevented the problem, and the fix arrives as an afterthought if it arrives at all.

Start here

  • Make contributing possible. An inaccessible dev environment, setup script, or docs site excludes the exact contributors you need. Test the contributor path with a screen reader and keyboard.
  • Answer accessibility reports in public and on a schedule. Say what you will do and when. Silence teaches people not to file the next one.
  • Pay or credit disabled testers. Lived experience is expertise. Treat it like any other specialist contribution rather than free QA.
  • Tag approachable accessibility work. Good first issues with clear reproduction steps turn interest into pull requests.
  • Run accessible meetings and events. Captions, agendas circulated in advance, a described screen share, and notes afterwards.
  • Name accessibility work in release notes. Visible credit is how the work becomes something contributors want on their record.
  • Connect to the wider effort. Assistive technology communities, other maintainers, and shared working groups reduce how much any one project has to figure out alone.

Signals of progress

  • Disabled users are involved before a feature ships, not only after a complaint.
  • Accessibility issues get a first response within a stated window.
  • The contributor setup path has been tested with assistive technology.
  • Accessibility fixes appear by name in release notes.

Phase 05 Sustaining

Keep the gains after the person who cared most about them moves on.

Accessibility programs usually fail slowly. Ownership goes unfilled, the statement goes stale, a dependency changes, and a year of work quietly reverses. This phase is about making the commitment survive turnover, budget pressure, and shifting priorities.

Start here

  • Track a small number of real measures. Open accessibility issues, age of the oldest one, regressions caught in CI, and time to first response tell you more than a conformance percentage.
  • Schedule a review per release. Tie an accessibility pass to a date or a milestone so it does not depend on someone remembering.
  • Keep the statement current. Update known barriers and test coverage when they change. A stale accessibility statement is a trust problem, not just a documentation one.
  • Plan for succession. Document where the tests, baselines, and decisions live, and have more than one maintainer who can run them.
  • Fund the work. Sponsorship, grants, or paid maintainer time is what separates a project that keeps up from one that has a good first year.
  • Watch what you depend on. Upgrades to frameworks, component libraries, and assistive technology change behavior. Retest after major bumps.
  • Record the decisions. Why a pattern was chosen and what was rejected saves the next maintainer from relitigating it.

Signals of progress

  • Accessibility measures are reported alongside other project health metrics.
  • More than one maintainer can run the full test procedure.
  • The accessibility statement has been updated within the last release cycle.
  • Accessibility work continues through a change of maintainers.

Contribute to the framework

The framework is maintained in the open by people from the disability, accessibility, and open source communities. It improves when maintainers who have used it say what worked and what did not.

    Tell us where a phase was unclear, missing a step, or wrong for your kind of project.
